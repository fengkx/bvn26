# 第七关重载与 26 位辅助的显存检查

11 月 27 日 14:11 导出的 iPhone 日志中，第七关「静涎亭」的玩家是一护卍解，搭配山中井野。电脑是日番谷卍解，搭配四枫院·夜一。保存的 1,036 条本局玩家输入均无召唤。电脑在第 18,189 个战斗刻进入召唤动作，第 18,190 刻转为受击，期间没有辅助出场记录。随后电脑血量归零，双方在第 18,498 刻回满血，旧页面最后记录停在第 18,575 刻，距离召唤起手约 12.9 秒。最后一次性能采样约 60 FPS，图形资源计数约 55.9 MiB。日志没有记下导致页面重载的系统原因。

## 修改及对照

- 碎蜂和志志雄·真实的部分特效在屏幕外继续分配大块缓冲。将直接绘制到舞台的无滤镜混合组裁到可见区域，并保留一像素采样边缘。需要给外层滤镜提供完整输入的组继续使用原范围。碎蜂的一张缓冲由 1129×829 降至 602×402。
- 逐帧冻结碎蜂、志志雄·真实、山中井野的 22 组同场景画面，在同一状态下分别渲染裁剪前后版本。碎蜂的最大 RGB 通道差为 2/255。全部画面最大为 7/255，出现在志志雄近身第 84 帧。
- 换关替换角色前，同步释放已经离开场景的上一组角色和辅助。以一护卍解、山中井野按闯关顺序分别启动前七关，原版本 Godot 静态内存峰值为 388,389,163 字节，修改后为 325,672,827 字节。这里测量的是桌面引擎的分配计数，iPhone 网页进程的峰值仍待真机验证。
- 同一帧出现多次闪光时，只注册一次绘制完成回调，记录最终显示的闪光。第七关在没有任何召唤的情况下击倒日番谷、进入第二回合也已单独复测。后续网页版检查点会保留回合号、开场状态和 Ready 动画帧。

[全辅助回归脚本](../../godot/tests/helper_roster_render_smoke.gd)会从选角目录自动读取当前所有辅助。可在已导入素材的项目上运行以下命令。

```sh
godot --path godot --rendering-method gl_compatibility --script res://tests/helper_roster_render_smoke.gd
```

## 网页版与回归范围

在本地用正式的 Web 导出流程构建游戏，测试入口复用上述回归脚本。导出核心包的 SHA-256 为 `5d772a3546ca7b2cad0c1587a4169c29deea46288aba2975e672b81390ae897d`。浏览器验证只替换测试入口和增加断言，战斗代码与角色包取自这次导出。

- Chromium 在 iOS 渲染预算下完成全部 52 次召唤。逐项比对，出场时长和缓冲像素峰值均与桌面 Godot 相同。全程没有重复注册闪光回调的错误。
- macOS WebKit 使用与日志相同的 iPhone 浏览器标识，测试程序逐帧驱动绘制，全部 52 次召唤通过。每位辅助两侧的出场时长和缓冲像素峰值都与 Chromium 相同。此方式可核对特效绘制、缓冲和退场，iPhone 真机上的帧率与系统内存回收行为仍待验证。
- 离屏边界、井野绑定、回合重置、电脑对战 KO、八关流程、资料哈希及交接文档校验均通过。
- 两项已有的联机快照测试仍失败。选定形态恢复和跨回合计时器恢复在改动前后的快照检查中均报 `Unaudited Main field: _pending_helpers`。
