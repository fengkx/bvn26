# R4 scalar-dispatch independent acceptance

## Verdict

**Scoped checkpoint correctness accepted.** The R4 change removes recursive
`_encode()` dispatch for a narrow set of values already returned directly by
that function. Reviewed source identity is `battle_checkpoint.gd` baseline
SHA-256 `16ebed2dc1fa5fc45f11c61053261db02255ce2474017de76ac0bea7e54f78fc`
and candidate SHA-256
`a95ed7636da80b918e8695d600d6fcb6c590de58a9d68fa0a2f3db41b515f201`.
`simulation_state.gd` and the `battle-local-pba-dict-flat-v2` graph format are
unchanged in this round.

The complete diff against the frozen R3 source only factors the existing
nil/bool/int/String/finite-float allowlist and applies that same test at array
entry, dictionary key/value, and ordinary object-field call sites. Other types,
including `StringName`, non-finite floats, packed values, objects, callables,
weak references, and resources, continue through the existing codec. Ordering,
container identity, checkpoint contents, and rollback behavior are unchanged.

The short profile counted about 1,766 direct-eligible scalar values per save,
roughly 52% of recursive `_encode()` calls in that sample. This is structural
call-count evidence only. The samples were not a paired timing experiment, so
this acceptance does not establish a frame-time or frame-rate gain.

Implementation commands and raw log paths are recorded in
[the implementation evidence](checkpoint-scalar-inline-r4-2026-09-28.md).

## Not established by this acceptance

The supplied cross-computer P1 log has no reliable build identity, so it cannot
show that this candidate was running. No post-change real two-peer WebRTC match
or stable same-build browser comparison was measured. A 30 Hz online match and
real-network frame-rate improvement therefore remain unverified; this scoped
checkpoint correctness result does not complete M4-03.
