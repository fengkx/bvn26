# 角色一比一还原与缺陷验收 SOP

适用于新增角色、招式和修复原版差异。核心原则：**验证一次完整生命周期，分别证明行为与画面一致；用例数量不能替代覆盖范围。**

本页规定执行顺序与交付门槛。源码五问按 [SOURCE_FIRST.md](SOURCE_FIRST.md)，受击链按 [HIT_RECEIVE_SOP.md](HIT_RECEIVE_SOP.md)，精度和平台要求按 [VALIDATION.md](VALIDATION.md) 执行，不另建一套冲突规则。

## 1. 固定问题与版本

先记录角色/形态、模式、地图、双方站位与朝向、操作序列、发生在第几次施放、是否经过暂停/受击/回合切换。截图只能证明该时刻的画面，不能证明输入、播放帧或前面的操作历史。

- 记录原版 SWF 哈希、当前源码版本及未提交差异、实际运行包哈希、引擎/浏览器、窗口缩放和访问 URL。
- 区分线上版本、本地 Web 和原生版；没有版本证据，不先归因于缓存或旧部署。
- 先利用现有证据缩小问题；缺少决定性信息时询问一次，同时继续独立的源码排查。
- 为问题写一句可观察的验收标准，例如：“同一场对战第二次下＋I，冰柱仍在第 670 帧读取的对手位置生成。”

产物：问题记录、输入/初始状态、版本信息和原始截图或录像。

## 2. 沿完整生命周期回答源码五问

从输入入口追到收招与下一次施放，不能停在“找到了正确赋值”。列出全部相关帧脚本、回调、PlaceObject/MOVE/移除、显式退出及无脚本帧；反编译有歧义时核对时间轴/字节码及原播放器。

对每个影响结果的状态补一张表：

| 状态 | 谁拥有 | 初始化/写入时机 | 保留条件 | 清除时机 | 源路径 |
|---|---|---|---|---|---|
| 播放头、局部坐标、命中标记、暂停状态、事件去重记录等 | 帧执行、招式、实例、角色或对局 | 具体帧/回调 | MOVE、相邻标签、暂停等 | 新实例、再次执行、移除、回合结束等 | 脚本与时间轴 |

检查重点：

- 新实例不能继承旧实例变量；保留实例不能因换标签被错误重置。
- 原版帧脚本再次执行时，移植中的去重记录必须允许本次执行；不能把“一次帧执行”误写成“整场对战只执行一次”。
- 同名、同深度、同一源放置帧不代表同一个运行时实例，需要区分创建代次。
- 不默认所有暂停都冻结所有回调，也不默认恢复后所有实例同时执行。出现一帧差异，记录实例创建与回调/帧脚本的实际顺序。
- 先补编译规则或共用调度，再让运行时解释；禁止按角色猜偏移、改框或补固定延迟。

产物：五问答案、状态生命周期表、源码定位；不明确的顺序标为待观测，不猜补。

## 3. 先保留失败，再修改实现

建立尽可能小、确实触发问题的失败用例，记录旧输出与失败原因。保留原输入、随机/时钟 tape 和比较精度；修复时不得改期望输出或放宽阈值掩盖差异。

同时保留两类用例：

1. **新对局基线**：证明首次施放、基础输入和配置正确。
2. **同一实例连续序列**：证明第二次、第三次施放及中断恢复正确。不能通过重新创建角色、重开测试场景或清空缓存绕过问题。

连续序列至少包含一次目标位置改变和换边；按缺陷涉及的状态加入打断、暂停恢复、回合切换或重新选人。需要补气/改站位的受控测试必须记录这些干预；它不等于真实输入整局对照，不能混入后者的通过率。

产物：能失败的回归、旧日志/截图、受控干预说明。

## 4. 行为与视听分开核对

| 维度 | 必查内容 | 不能替代它的证据 |
|---|---|---|
| 输入与调度 | 按下/保持/释放、消费阶段、回调顺序、暂停与延迟脚本 | 最终血量相同 |
| 角色状态 | 源帧、坐标、朝向、动作、HP/气量、受击/接触/连击 | 游戏能运行 |
| 特效实例 | 元件、名字与创建代次、父级、局部/世界坐标、播放帧、显示列表寿命 | 对手确实受到伤害 |
| 画面 | 注册点、完整变换链、形状路径/裁切、遮罩、层级、混合、相机 | 角色状态轨迹匹配 |
| 声音 | 触发次数与时点、片段、音量/包络、暂停及清理 | 音频文件存在或流长度正确 |

发招、首次生效、元件替换、收招、消失及再次施放都要检查，不能只选最好看的一帧。原版与移植应对齐逻辑帧、坐标与缩放；无法对齐时明确记录限制。

贴图偏移/缺块按以下链排查：**源位图 → Shape 路径与填充矩阵 → 子实例局部变换 → 角色外层矩阵 → 世界/相机 → 前景与遮罩 → 平台渲染**。包围盒不是实际填充形状。先看错误轮廓是否对应资源或裁切边界，再用同位置隐藏地图层的隔离实验验证遮挡假设；诊断开关不进入生产行为。

产物：同阶段轨迹、关键帧对照、差异首发点；视听未测时单独保留未验收状态。

## 5. 用原播放器验证原因

按已有授权与捕获工具约定，在独立副本插桩，保存输入、初始状态、源码哈希、插桩 diff、原始日志及捕获完成状态。工具不得改变原实例创建顺序、随机消费或待验证的控制流程。

- 两端重放相同输入，比较第一个分歧，沿因果链回查；不要只比最后结果。
- 调度问题同时观察相关角色、援助、特效的创建/移除、回调和帧脚本边界。
- 记录实例位置才能证明定位；仅记录角色位置不能证明特效定位。
- 受控跳帧、合成场景、原生单测、Web 回放、原播放器整局对照分别标注。每类证据只证明实际观测的字段与条件。
- 新增观测器后与保留轨迹核对已有字段，避免插桩改变被测行为。

没有相应原播放器证据时，可以报告源不变量回归通过，但该范围仍不得称为原版同输入验收通过。

## 6. 修复后按影响面回归

先确认同一失败用例变绿，再验证相邻边界和共用路径。按改动影响选择检查，不机械重跑全项目，也不因一次通过就跳过直接受影响的路径。

| 改动 | 至少追加的检查 |
|---|---|
| 坐标/事件去重/实例状态 | 同一角色连续施放、双朝向、目标位置变化、保留实例不误重置 |
| 裁切/渲染器 | 变更前后元件、发招与收招、同位图不同形状、镜像/缩放、实际 Web 画面 |
| 共用调度/暂停 | 新旧实例交错、双方互攻、援助、受击/防御、恢复边界、相关模式与退出清理 |
| 转换器/共用机制 | 列出所有受影响使用方，运行其代表性原版对照与边界用例 |
| 输入/场景生命周期 | 保持与释放、失焦恢复、重新施放、下一回合、返回再进入 |

原生通过后，在实际 Web 构建中验证涉及的路径。浏览器调用诊断脚本通过不代表真实键盘、失焦或恢复也通过；逐项报告。涉及声音/图像的修复不能只拿状态 JSON 哈希作为最终证明。

工具/资料变更运行 `python3 tools/verify.py`、`python3 tools/check_handoff.py`；契约变更追加 `python3 tools/validate_contracts.py`。哈希不符先核差异，仅更新已审查的合法变更；保留无关工作。

## 7. 分开报告修复、验收和发布

为每项记录“已匹配、存在差异、未验证、明确暂缓”，并附证据。修复完成必须有原失败回归、相关影响面检查和清楚的剩余范围；完整角色验收仍须满足验收矩阵，不能用单个缺陷关闭来替代。

- 实际招式、能量不足的负例、原版缺少标签的无动作分别计数。
- 报告“167 个场景的角色状态匹配”，不要省略范围写成“角色全部一比一”。
- 分别说明代码修复、本地原生、本地 Web、线上部署及线上复测状态。部署成功还须核对实际运行版本，并重放用户路径；本地导出不等于网站已更新。
- 遵循已有部署授权，不因本页重复请求许可，也不自动把本地任务扩展成线上发布。
- 更新 `docs/STATUS.md`、`plan/tasks.json` 的证据、剩余项与实际投入，不把未测项改成完成。

交付记录可直接使用：

```text
问题及触发历史：
原版依据（源路径/帧/实例/原播放器轨迹）：
根因与状态所属生命周期：
失败回归 → 修复后结果：
连续施放及边界覆盖：
角色状态 / 特效实例 / 图像 / 声音分别验证了什么：
原生 / Web / 线上版本与结果：
仍有差异 / 未验证 / 暂缓项：
证据路径：
```
